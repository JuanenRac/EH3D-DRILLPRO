# Changelog

All notable changes to this project are documented here.

## [Unreleased]

- **The node of the drill head in the machine file:** `head_node` (`off`, `direct` or `server`), `head_address`, `head_token` and `head_camera` say how EH3D-NODE-BUNGARD-AUX is reached; they are written only when the node is used, and the other lines of the file stay as they are.
- **A table that is not flat:** the options of a job can carry the height map of the table, and every hole is drilled to the same depth into the board wherever the table is high or low (`plan_drill_job_levelled`); without a map nothing changes.
## [0.0.6] - The connection drop-down, a blinking cursor, tabs for panels, jobs that go on and the machines of the fleet

- **A job can go on:** the options of a job tell how many of its first holes are already done, and the job leaves them out; the desktop window opens maximized.
- **Tabs for the outside of a panel:** a panel can carry tabs (how many on each side, how wide, spread evenly, near the ends or together in the middle) and the routing of its outside is cut into the pieces between them, so the boards stay joined to the panel until they are broken out.
- **The connection chosen in the Config window:** a drop-down with the five ways the job reaches the machine (the simulator, the serial port, a USB adapter, the EH3D node, the EH3D server) and what each needs (a port, an address and a token, a machine of the server); it is checked, applied with OK and written into the machine file without touching its other lines. The same for EH3D-ROUTEPRO.
- **A blinking cursor:** the cursor of a field being edited blinks. The same for EH3D-ROUTEPRO.
- **`--keys` takes `tab` and `backtab`:** the pictures of the windows that need them.
- **The order of the holes:** the classic screens tell, through `hole_order`, the holes of the job in the order the machine drills them, so a window that draws the board marks the right ones.
- **Several machines and stations at once:** with `connection = server`, `drillpro --machines` asks the server for the whole fleet in one request and lists every machine, grouped by station, with what each one is doing, its job and the jobs ready; `--machine ID` sends the jobs to that machine instead of the one in the machine file; the client reads the answer with `eh3d-fleet` (tested on a server that answers one request, and against the real server in EH3D-SERVER).
- **The buttons answer to the pointer:** the button under the pointer lights up, and while it is pressed it sinks (it loses its shadow, goes darker and moves its letters a little); `--point COLUMN,ROW[,down]` puts the pointer there for the pictures.
## [0.0.5] - The machine files from a shared crate, sounds for the end of the job and the tool change, more patterns in the file window and screenshots

- **The classic main screen names the program that runs:** the heading under the logo says which program it is (the routing program no longer says it is the drilling one).
- **Screenshots in the README:** three pictures of the classic screens (the main screen, the tool data and the parameters) in all the eight languages of the README.
- **More patterns in the file window:** an engine can add patterns after its own (the routing program adds the drawings of a board), which the arrow next to the file name lists with `*.ZIP` and `*.*`.
- **The files of the machine come from a shared crate:** the drill file, the tool table and the machine configuration are read and written by `eh3d-bungard-formats` of EH3D-COMMON (the same code that ROUTEPRO and the modern interface use); nothing changes for the operator.
- **Sounds when the job ends and when the machine asks for a tool:** `sound_finish` and `sound_tool_change` in the machine file are each off (the default), `default` (a tone the program makes, one for each cue) or the path of a WAV file of the operator's. The sound is played by the system (PowerShell, `afplay`, `paplay`/`aplay`/`play`) in a process of its own, so it never stops a job. It is explained in the machine file and in the guide of the configuration in the eight languages.

## [0.0.4] - Jobs in ZIP archives, an Offset window that moves the machine, file patterns and a simulation at the speed of the machine

- **The simulated job follows the clock of the machine:** the engine can be advanced by seconds of machine time (`tick_for`), so a move on the simulator takes as long as it would on the machine, with the feeds and the speeds of the tools, instead of running as fast as the computer can.

- **A lighter debug build:** the `dev` profile keeps the file and line of a panic (`debug = "line-tables-only"`) but not the full debug symbols, so the `target` folder of a test run is about a tenth of its size.
- **The Offset window moves the real machine:** with a real connection (RS-232, USB-RS232 or the node) the machine homes when the Offset Teach window opens, follows every move of the window (X, Y and Z, in steps of 1, 10, 100 or 1000 mil) and goes home again with the drivers off when the window closes; the window says when it is homing and shows a failure of the link. Through the EH3D server the window does not move a machine and says so. On the simulator it only follows the position on the screen, as before.
- **The arrow of the file name opens a list of patterns:** `*.NCD`, `*.ZIP` and `*.*` (`*.DTD`, `*.DCF` and `*.*` for the tool and configuration files); the list of files follows the pattern, and job archives are listed when the pattern asks for them.

- **Buttons that did nothing now work:** Start and Panelz. without a file say "Load a file first" in a window instead of staying silent; the Load button of the Tool Data and Parameter windows opens the Select File window for the tool files (`*.DTD`) or the configuration files (`*.DCF`) of the program and loads the one chosen, saying which; the arrow at the end of the name field of Select File gives the keys to the list of files.

- **Jobs packed in ZIP archives:** the Select File window lists the `.zip` files of a folder like folders, goes inside one with Enter (or by typing its name) and shows the drilling files in it; a file is taken out into a work folder and loaded as any other. `drillpro JOB.ZIP` loads the first drilling file of the archive. The archive code is the shared `eh3d-archive` crate of EH3D-COMMON, which never lists a name that could leave the work folder.

- **A metric header is read as metric:** the `METRIC` line of the header of a drill file begins with an M and was taken for a command, so the diameters of such a file were read as inches. Now it is read as it says.

- **The build, build-test and test scripts show a live panel:** a banner with the name and version, one line per step with its time, the number of tests that passed and a summary at the end, with the whole output kept in a log file. `test.sh` and `test.bat` run only the tests and never change the version; without `tools/pretty_run.py` the scripts behave as they always did.

## [0.0.3] - The Offset teach-in, the tool changer of the ATC models, examples and a 32-bit Windows build
- **A basic configuration and examples in every release, and Windows 32 bits:** the packages now carry the machine and tool files with every line explained in plain words, a guide to them in the eight languages, the example connection file and an `examples` folder of drill files from one hole to twenty thousand; all of it is generated by scripts in `tools/` and read back by a test. The release builds also include Windows 32 bits (not tried on a 32-bit Windows).
- **The operator's dialogs in the classic screens:** the job asks, as the original does, to confirm that the spindle may start (Attention!) and, for every tool, to put it in (Tool Change: the tool, the length of the run, the spindle, the Z speed and the stroke), with Ok and Abort on the keyboard (`Enter`, `Esc`, the letters) and the mouse. The simulation stops there too, so the whole flow can be seen without a machine. Before, a job on a real machine had no way to answer these dialogs from the classic screens (the menu-driven interface did) and would wait for ever.
- **The tool changer of the ATC models (basic):** when the configuration file has the "Tool change 1=Auto" line and the rack positions, DRILLPRO changes the tools by itself: for every tool the head goes to the place of the tool that is in the chuck (place 0, the test pin, at the start), lowers Z, opens the chuck with the auxiliary output, slides to the place of the next tool, closes the chuck and goes on to the first hole; the last tool goes back to its place. The Parameter window has the **AutoChg** box of those models (`U`, or a click). A job with more tools than places in the rack is refused with a message. The sequence follows a recording of the original on an ATC model, event by event; **it has not run on a real ATC machine**, and the test pin, the drill break detector and the tool-damage check are not done yet. The manual models are not affected: the job they get is the same as before.
- **Steps on a half step:** a hole that falls exactly half way between two steps now rounds to the even step, as the original does (it showed in the recording of the changer).
- **Vacuum cleaner on the auxiliary output (optional):** `vacuum = aux` in the machine file switches the auxiliary output (latch A bit 5) on with the spindle, at its speed, and off with it. The default, `vacuum = central`, writes exactly what the original software writes on the manual machine (which never touches that bit: a relay wired to the control unit follows its spindle bits).
- **The Offset button works:** it asks "Delete old offset?" (Yes starts at home, No at the offset in the form) and opens the Offset Teach window as the original has it. The head moves in steps of 1, 10, 100 or 1000 mil (0.001 inch) with `E`/`S`/`D`/`X` (Y+, X-, X+, Y-) or the arrow keys, `R`/`C` or `PageUp`/`PageDown` for Z, `1`-`4` for the step, and the mouse on every button. The position is shown in mm and Z as the depth left. **Ok** writes the position into the Offset fields of the main screen. **Teach** starts the Teach-In mode: positions are relative to the point where it was pressed, `+ Pos` records the head position, `- Pos` takes the last one back, `Mod` puts the last one where the head is, and Ok asks "Write Teach-In file?" and writes `TEACH.NCD` (a drill file this program reads). Screens checked against the original.
- **Esc during the job asks what next:** as the original does, `Esc` while drilling or routing opens INTERRUPTED / What next? with Cont. and Abort (keys `Enter`/`C` and `Esc`/`A`, or the mouse). The job waits, with the machine still, until the operator answers; Abort stops it and brings the form back. Before the first move (homing) `Esc` still stops at once.
- **The mouse wheel** scrolls the file list (window and console).
- **The percentage** of the job window counts the holes done, as the original does.
- **Moving through the folders of the computer:** the Select File dialog lists the files, then the folders, then `..\` last, as the original does; it works from the absolute folder (a folder written as `.` could not go up before), shows the drives as `[-C-]` entries on Windows, hides dotted files, ends a long name with `~`, and tells when a folder cannot be opened. A path written in the name field (`D:\jobs\*.NCD`, `..\other`, `C:\`) goes to its folder and takes the rest as the pattern or the file; the name field takes a path of any length. The mouse wheel scrolls the list.
- **The form drives the job:** the vectors `from` and `to` choose the holes (or paths) that are done, the clip leaves out the ones that end outside the working area (counted), and the Panelization dialog's Ok repeats the job over the copies, a tool at a time so that there is one tool change; the copies are `board - spacing` apart, as the original's count works out.
- **The job window shows the job:** the position, the tool, its stroke, the speeds, the count and the drilled depth follow the planned job (the values are the planned ones, not read from the machine).
- **Enter walks the form:** accepting a field goes on to the next one, as in the original.
## [0.0.2] - The classic screens, the mouse, the real files and a console version

- **Console version:** `drillpro-console` draws the same screens in a terminal, with the keyboard and the mouse, and needs no window system: it runs over SSH, on a text console and on an old PC, in the MS-DOS spirit of the original. The terminal must be 80 columns by 25 rows or larger; a larger one shows the screen in the middle.
- **Packages:** the release carries, for Windows, Linux and macOS (Apple silicon and Intel), the program with its window and the console version, each with its SHA-256.
- **One command line:** the window and the console read the same options (`--lang`, `--data`, `--connection`, `--modern`, `--dump`).
- **Classic screens (the default):** the main form (scale, offset, clip, vectors, board, base), the Parameter, Tool Data, Select File, Panelization and Quit dialogs and the homing and job windows of the MS-DOS program, drawn cell by cell in the same layout and colours, with every text in the eight languages. `--modern` starts the menu-driven interface as before. The classic screens are a shared front end (`classic`) that DRILLPRO and ROUTEPRO both use; a test per screen compares it with screens captured from the original when `EH3D_ORIGINAL_UI` points to them, and further tests check the hot letters, the label widths and the keyboard flow in every language.
- **Chord angle:** the configuration of the routing program is read with its chord angle (`Config::route_settings`) instead of the drilling sorting.
- **Editing and the mouse:** every field takes typing, `Backspace`, `Delete`, `Home`, `End` and the arrow keys (the first key typed replaces the whole value), `Tab` and `Shift+Tab` move between fields, `Enter` accepts and `Esc` cancels. Every field, button, radio button, list entry and dialog button answers to the mouse; a double click opens a file.
- **A window that scales:** it can be maximized or resized; the screen grows from 640x400 up to any larger size (480p, 720p, 1080p and everything between) keeping its proportions, and clicks follow the scaling.
- **Real files:** the Parameter dialog edits the machine configuration and writes it back to the real file (the old one stays as `.BAK`, every comment and reserved line is kept), reloads it, and holds the language; Tool Data edits the tool table and saves it; Select File filters with patterns (`*.NCD`, `T*.PLT`, ...) and lists a folder of any size in pages; the program starts in the folder the configuration names; leaving offers to save the changed settings. Without `--data` the files are looked for in the current folder, the folder of the program and the user's configuration folder.
- **About:** the program, its version, licence and source, and the Bungard machines it knows: CCD and CCD/2 with manual tool change (MTC) supported, with automatic tool changer (ATC) not yet, tried on a CCD MTC only, and a note that the project is independent of Bungard Elektronik.
- **The layout of the README is checked in the CI:** the validator runs `tools/universal_readme_check.py` and lists, as a warning, what differs from the universal layout of the README.

## [0.0.1] - First version: file readers, job planning, text-mode interface and a simulated machine

- **Excellon reader:** `.NCD` drill files with or without the `M48` header, modal coordinates and imperial units of 1 mil, with the tool table (`.DTD`) and the machine configuration (`.DCF`).
- **Job planner:** orders the holes as in the file, X first, Y first or by shortest path, grouped by tool.
- **Interface:** an 80x25 text-mode screen with CGA colours, menus, a file dialog and a vector view of the holes, in eight languages (English, Spanish, Italian, German, French, Portuguese, Chinese, Japanese).
- **Protocol library (`eh3d-drillpro-protocol`):** byte transport (serial port or simulator), motion planning in millimetres with acceleration ramps, and a safety gate that refuses motion until it is armed with verified settings.
- **Simulator:** the whole job runs to the end without hardware.
- **Real machine:** a machine file (`machine.cfg`, shared by DRILLPRO and ROUTEPRO) chooses the simulator, the computer's serial port, a USB serial adapter or the EH3D-NODE-BUNGARD; every tuning value lives in it. `Esc` stops a drilling job and switches the drivers off, and a red banner says the machine is real.
- **Reference run:** Z, X and Y to their limit switches with the control unit's "all home" line read once the last search has gone out (reading it in the middle of the stream made the Y motor lose steps on the CH340), a short unstick move when parked, a Z search that covers the whole travel (`z_search_steps`) and a smooth calibration jump. Tried on a Bungard CCD MTC; the CCD/2 MTC is driven the same way and has not been tried. Spindle and vacuum outputs have not been tried; the two ATC models are not covered.
- **Spindle of the node:** `spindle = node` in the machine file makes the job ask the EH3D-NODE-BUNGARD for the spindle (a variable-frequency drive on the node's own outputs, any speed up to the node's maximum) instead of writing the control unit's spindle bits; the spindle is stopped on any stop. The node link also reads the machine's lamps and can ask the node to drop the rest of a search as soon as an axis is home.
- **Server connection:** `connection = server` sends the drilling job to the EH3D-SERVER, which plans it with the constants of the machine, runs it through the machine's node and tells the program how it goes; the program shows the progress, answers the dialogs and can stop the job, and closing it does not stop the job.
- **Steady motion:** moves go out as one continuous stream paced by the adapter's UART, Z moves byte by byte.
- **Documentation:** protocol notes, the connection guide with the CH340 findings, and a machine file example with every value.
- 123 tests, `cargo clippy -D warnings` and `cargo fmt --check` in CI on Linux and Windows, and a repository check of the manifest, the versions, the changelog and the eight README files.
- **Ready-made packages for Windows, Linux and macOS:** the `Release binaries` workflow builds the program with its window for Windows (zip), Linux (tar.gz; X11 and Wayland) and macOS (Apple silicon and Intel, tar.gz), each package with its SHA-256, and the release carries them.
