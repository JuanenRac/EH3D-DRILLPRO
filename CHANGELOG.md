# Changelog

All notable changes to this project are documented here.

## [Unreleased]

- **The CI keeps its actions up to date and does not pile up runs:** a `dependabot.yml` groups the updates of the GitHub Actions in one monthly request, a new push to a branch cancels the run of the older one that is still going, and the Rust jobs have a time limit, so a stuck job cannot hold a runner for hours.
- **Tests of the files that cannot be loaded:** a file that is not there or a folder is an error on the screen and the file already loaded stays; a file of nothing but comments and blank lines is either taken with no holes or turned down with a reason, never a panic.
- **The frames of the link to the node are tested against shared vectors:** `protocol/tests/frames_vectors.rs` reads `protocol/tests/testdata/frames.json`, the file the firmware of the node tests its C++ code with, and checks that `encode` writes those bytes, that the decoder reads them back one byte at a time too, and that damaged streams (a wrong CRC, a length beyond the maximum, noise or a false start before a good frame) are counted and the good frames still come out.

- **The selection of a job takes its rule from the shared crate:** `job::vector_range`, `job::panel_offsets` and `job::inside_work_area` now call `eh3d_bungard_formats::selection`, where the rule lives for every program; what is selected does not change.
- **The direction of Z has a type of its own and one table of bytes:** `bits::ZDir` (`Up`, `Down`) gives the step byte of each direction (`step_byte`) and reads it back from a byte (`of_step_byte`, which says nothing for a byte that does not step Z); the planners of the job, the homing, the movement of Z and the simulator ask it instead of repeating `Z_POS` and `Z_NEG` and the direction bit. The bytes on the line do not change. A test checks both directions and the bytes that are not steps of Z.
- **The selection of the vectors of a job is one piece of code for the drilling and the routing:** `job::vector_range` (the first and the last vector a job takes), `job::panel_offsets` (where each copy of the board goes on the panel) and `job::inside_work_area` (whether the points fall inside the working area once the offset of the machine file is added) are used by the selection of the holes here and by the selection of the paths of ROUTEPRO, so both cut the panel and the working area the same way. Three tests check the range, the grid of the panel and the edges of the working area.
- **A drill file past the limits of the readers is refused with its code, and a big one is said:** loading goes through `ncd::parse_limited` with the limits of `reader_limits.cfg` of the shared crate (bytes and lines, a hard and a warning value for each), so a file past a hard limit is refused with `EH3D-FORMATS-011` in the language of the screen and a file past a warning limit is read and the line under the file says that it is big, in the 37 languages. A test loads a drill file past the warning limit.
- **A closing or a place of the tool changer that cannot be right is turned down before the job is planned:** when a job starts, `check_rack_options` is run on the options of the job (a first place or a list of places over the limit, place 0, a tool with two places, a place given to two tools, a place for the tool in the chuck without saying it comes holding one, or a place that is also a tool's), whether the job goes to the server, to the node or to the simulation, and the screen shows the same sentence the server gives (`bad_rack: ...`). A job with a valid rack starts as it did.
- **The warnings of the server about the request are shown under the job in the language of the program:** `rack_unknown_field` (with the name of the field), `request_version_newer`, `rack_needs_v2`, `rack_no_changer` and `out_of_course` (with the axis and how far past the course) are told in up to four rows of the window of a job on the server, in the 37 languages of the shared texts (`warning_text`, `warning_lines`); a code the program does not know is not shown, and a text that comes from the server loses its control characters and is cut before it is written on the screen.
- **`out_of_course` is read from the answer of the server:** `AnswerWarning::OutOfCourse` holds the axis and the excess in thousandths of a millimetre (a missing or negative excess is 0), and the notes of the job on the server (`ServerNotes::warnings`) keep every warning of the answer.

## [0.1.6] - The contract of the job with the server, guards for the input files and the zip library at 9

- **The contract of the job request is in one place (`work_contract`):** `check_rack_options` makes the checks the server makes of a `rack` (`bad_rack`: `first` and the number of places over the limit, place 0, a tool or a place given twice, `carry_slot` without `carry_in`, at place 0 or taken) in the same order and with the same sentence, `refusal_detail` tells what the local planner refuses with the words of the server, `chain_answer` reads `rack_applied` and the warnings `rack_needs_v2`, `rack_no_changer`, `rack_unknown_field` and `request_version_newer` (a code it does not know is kept), and `unknown_rack_fields` and `chain_options` hold the request to the fields the server knows and read it back. The run window notices a rack that was not used through the same reading. With tests of every sentence and code, of the order of the checks, of the round trip of the request and, when the repository of the server is next to this one, of the sentences and codes against its documented contract.
- **The files that are read have limits (`input_guard`):** a drill file that is bigger than 64 MiB, has a character 0, a line of more than 16384 characters or a number of more than 40 digits in a row is turned down when it is loaded, with the stable code (`input_too_large`, `input_binary`, `input_line_too_long`, `input_number_too_long`) and the number of its line; files of real boards are far inside the limits and load as before. With tests of each limit, of the first problem found and of the sample files.
- Update the zip library to the version without the known vulnerabilities.
- Screenshots of the application in the README.
- **The tools of a job can be taken from the places of the rack that the person gave them:** `JobOptions` has `rack_slots` (the tool number and its place) and `rack_carry_slot` (the place of the tool the chuck comes holding), and the rack of the job carries them: every exchange of the job - taking a tool, putting the used one back, the one the chuck hands on to the next job and the last one at the end - goes to the place given to that tool, and a tool without a place is taken from the place the order of the job gives it, as before. A job with places is refused, with the number of the place, when one is not defined in the machine file or is where the machine does not reach. The request to the server carries them in `rack.slots` and `rack.carry_slot`. With tests of the order of the chuck for places that are not in the order of the job, of the chaining with places and of the checks.
- **A drilling job sent to the server carries the chaining of the tool changer:** the request has the optional `rack` field (`first`, `carry_in`, `carry_out`, with `request_version` 2) when the job is one of a chain, and is the request of before when it is not. A server that turns the field down (400 or 422) gets the job again without it, and one that does not answer `rack_applied` is noticed too: the run window says in red that the tool changes were not chained. With tests of the request with and without chaining.

## [0.1.5] - Audit fixes, the new reading limits, tests and the application icon

- **The Windows executable carries the icon of the program:** the file shows it in the explorer and the taskbar, together with the name, the description and the version, embedded by `build.rs`; other systems are not affected.
- **The window carries the icon of the program:** the title bar and the task bar show the icon of DRILLPRO.
- **The application icon and the logos of the program:** `images/brand/` holds the icon (SVG, PNG sizes, `.ico` and `.icns`), the horizontal and vertical logos in a light and a dark version and the social preview image.
- **Release builds are checked and attested:** `release-binaries.yml` takes the owner's go-ahead only (a manual start from main, the commit must be part of main), builds the same packages as before, writes `SHA256SUMS` and a build manifest, attests their provenance, verifies the artifact as a stranger would, prepares a draft release of unsigned files only after the owner approves it (a dry run is the default) and opens an issue `build-failed` when anything does not finish.
- **A plan on paper with no machine (`drillpro-plan`):** `drillpro-plan FILE.NCD [--data DIR] [--lang CODE]` and `App::plan_report` work out what a job would do with the holes, tools, rack and machine file that a start uses and print the facts (holes, tools, steps, holes left out) and the summary (how far each axis goes, the time, the checks of the work and the verdict against the course), in any of the languages of the program. It needs no connection and sends nothing; an option it does not know, a language it does not have or a file it cannot read is an error with exit code 1.
- **Stored plans of the sample files:** `tests/plan_golden.rs` compares the plans of `T1.NCD`, `14TOOLS.NCD` and `refholes.ncd` (English) and of `T1.NCD` in Spanish with the copies in `tests/golden/`; a change that is meant is stored again with `EH3D_UPDATE_GOLDEN=1`. It also checks that the facts do not depend on the language, that the same files give the same plan twice and the command line.

- **The README says what the ATC models do:** it no longer says that they are not supported; the tool changer follows the rack of the machine file and has not run on a real machine.
- **`job_rack` builds the rack of the tool changer from a machine file and says why a job is refused (`RackRefusal`):** more tools than places, a place with no position or a place the machine does not reach; DRILLPRO, ROUTEPRO and the modern interface use the same function, with the words in the 37 languages.
- **Where the head is during a simulated job, from the steps of the plan:** `Progress::with_track` follows the steps of the items from the switches and `ClassicEngine::head_mm` gives the head's X, Y and Z at any moment, so a view can show the trips to the tool bar and the exchanges of the tools, not only the hole that is next.
- **`JobBuilder` can change tools from a rack:** `with_rack`, `has_rack` and `chuck_swap` plan the exchange of the tool in the chuck for the next one (place 0 is the test pin), which is what a routing job needs on the machines with the tool changer.
- **More tests:** the planning of moves in steps and millimetres, the rounding of the original, the values of the machine file and their ranges, the answers of the server as they come on the wire, and the command line.
- **An answer of the server with a chunk size that is impossibly big** is refused instead of stopping the program.
- **The workflows are hardened:** every action is pinned by its commit with its version in a comment, the checkouts keep no credentials, and the release workflow runs only for the owner on main, with no cache and the values of the matrix passed by environment.
- **A rack with no places** no longer stops the program when it is checked against the reach of the machine: it has no place that is outside.
- **More tests:** the gaps and the reach of the rack of the changer, the lane over the tools and the bytes of a plan.

## [0.1.4] - Shared summary, progress by time and a machine file from the start
- **The dry run and the summary before a start live in EH3D-COMMON (`eh3d-summary`):** `dryrun` and `summary` keep their paths and their functions as before, but the measure, the sanity checks, the summary and the words of them (now in `eh3d-view`, in the 37 languages) are shared with the other programs; `Summary::refusal` takes the `Limits` that `summary::limits(&tuning)` gives.

- **A folder with no machine file starts from the one that comes with the program,** so the settings (the bar of the tool changer among them) can be changed and saved there; before, every change was silently lost until a `DRILLPRO.DCF` was put in the folder. With tests.
- **The plan says where each hole ends:** `plan_drill_job_marked` gives the item that ends every hole beside the items, and `JobBuilder::mark_done` and `finish_marked` do the same for jobs that are not holes. The holes done now come from those marks, not from guessing them out of the shape of the steps.
- **Progress by time, and the time left** (`eh3d_drillpro::progress`): the share of the job done is the time of the items already done over the time of the whole plan, so a reference run no longer counts as much as one hole; the window of the run shows the percentage, a bar that follows it and the time left.
- **The errors of the link are told in words:** `ConnectError` and `HomingError` have a readable message, and the failures of a run say what was being done (connecting, the reference run, the move) instead of showing the name of the error type.
- **`test.sh` and `test.bat` run the tests of the whole workspace,** the protocol crate included.

## [0.1.3] - Summary and dry run before moving a machine

- **A dry run of the exact plan** (`eh3d_drillpro::dryrun`): the steps of a planned job are followed on paper, decoded the way the control unit reads them, to measure how far each axis goes from its switches, where the plan ends and how long the movements take; a plan that takes an axis past the course of the machine file is found before a motor turns. Shared by the programs, the interface and the server.
- **A summary before a job moves a real machine** (`eh3d_drillpro::summary`): what the job does, how long it takes, how far each axis goes and what looks wrong in the file (a work that is tiny or far from the corner of the table, bigger than the table, or stretched by a scale that is not 1), in the 37 languages. The text screens and the classic screens show it and the job starts only when it is accepted; a plan that would take an axis past its course is refused. The engines of the classic screens offer `pending_summary`, `accept_summary` and `decline_summary` to the interfaces.
- **Four new keys of the machine file:** `confirm_start` (on), `dry_run` (`reject` by default, or `warn`), `dry_run_margin_mm` (0.5), `sanity_tiny_mm` (5) and `sanity_far_mm` (150), with their lines in the example file and in `docs/CONNECTION.md`.
- **The note of BOARD THICKNESS in the sample machine file** now matches its value (1.00 is the value of the original file; 1.60 is written for a usual 1.6 mm board); before it said 1.50 was the usual one.

## [0.1.2] - A failure inside the work is told and stops the machine, a record of crashes, a self-test for the machine and a CI that builds the interface

- **A machine self-test:** `tools/machine_selftest.py` reads `DRILLPRO.DCF` and the tool table and checks them against the model of the program (speeds against the serial line, acceleration against the ramp, spindle start time, tool speeds against the spindle, depth, calibration factors) and writes `machine_selftest_drillpro_<time>.txt`. `--measure` guides a stopwatch measurement of the acceleration and the spindle start time and writes a proposed machine file as a new file, never over the machine file. It sends nothing to the machine. Its tests run in the CI.
- **`docs/HARDWARE_CHECKLIST.md`:** the steps to do by hand on the machine, with what must happen and where to write the result.
- **A failure inside the work is told, and the machine is stopped:** when the thread that runs a job (or the Offset window) panics, the run no longer stays at "running" for ever with nothing said: the machine is stopped first and the state becomes failed with "internal error" and the words of the panic.
- **A record of crashes:** a panic is also appended to `eh3d-crash.log` in the configuration folder (`%APPDATA%\EH3D`, `~/.config/eh3d`) with the program, its version, the words and the place, because a window program on Windows has no console to show it.
- **The CI builds and tests the graphical interface too** (`--features gui`, with the libraries of the window system on Linux), and checks the pictures of the README; the architecture picture pointed at files that no longer exist and now points at the ones that do.

## [0.1.1] - Cautious values named, acceleration and spindle start counted and a rack gap that stops the job

- **The tools that run with the cautious values are named:** a tool of the job that the tool table does not give (or whose line could not be read - a field missing, a letter in a number - which is then shown) is drilled with the cautious defaults as before, but the screen says which tools they are before the job goes on; the decimal comma of a Spanish or German Windows is read in the tool table.
- **The acceleration and the spindle start time of the machine file now count (not tried on a real machine):** `ACCELERATION` scales the length of the ramps - with the values that ship (10 for X and Y, 20 for Z) they are what they were, 5 makes the ramps of X and Y twice as long ("if the motors stall at the start of a move, try 5"), a higher number makes them shorter - and `SPINDLE START TIME` is the seconds to wait for each 10000 rpm for the spindle to reach its speed (0.50 gives 3 s at 60000 rpm; the 1680 ms that were fixed before are 0.28). A machine with no file keeps the fixed 1680 ms. The numbers are pinned by tests; the effect on the motors and the spindle has not been seen on a machine.
- **The request to the server cannot be split:** the names of the machine and of the jobs are written into the path as one safe segment (everything but letters, digits and `-._~` as `%XX`), and a path, an address or a token with a space, a control character or a line break is refused before it is sent. The token goes in the clear over plain HTTP: use it on a network that can be trusted or through a tunnel.
- **A gap in the rack of the tool changer stops the job:** a place with no position in the machine file is never gone to (it used to send the chuck to the origin of the table); the message gives the place.
- **The height map and the server:** a job that goes through the server is not started with a height map in use, because the server plans on a flat table; the screen says so instead of ignoring the map.
- **Slots are not lost in silence:** a drill file with slots or routed moves (`G00`/`G01`, `M15`/`M16`) is refused with the first of those lines, and a headerless body that ends in a `%` keeps its holes.
- **The connection to the node has a time limit** (three seconds for each address): a node that is off or has another address no longer leaves the window waiting for a minute or two.
- **Four new texts in the 37 languages;** `Rack::new` and `Rack::first_gap` in the protocol; tests for the tool table, the slots, the gaps of the rack and the connection.

- **The tool change of the ATC models goes over the tools:** the tool in the chuck is put back in its own place, the chuck rises over the shanks of the tools of the bar, goes to the place of the next tool, comes down, takes it and rises to home again. Each place is entered from the free side of the bar (a few millimetres along X, set in the machine file), the height of the empty chuck comes from the length of the tools and the clearance kept in the same file, and a place outside what the machine reaches stops the job with a message, as a place with no position already did. The exchange recorded on the original machines is still what a rack with no travel data plans. **The new movements have been checked on the planned steps and on the simulator only, not on a machine.**

- **Cut, copy and paste work in every field:** the window was built without the clipboard, so Ctrl+C, Ctrl+X, Ctrl+V, Ctrl+Insert, Shift+Insert and Shift+Delete did nothing. The fields of the classic screens (drawn by the program, one line each) take a pasted text in place of the selection or at the cursor, only its first line, only the characters the field takes and no more than it can hold; Ctrl+A selects the whole field; the right button opens a menu with Cut, Copy, Paste, Select all and Undo (the entries that do not apply are greyed out, Paste also when the clipboard has no text), named in the 37 languages. 6 tests of the field.
- **Full screen:** a check box in the Parameter window and the F11 key make the window fill the screen or give it back; the choice is kept in the settings file that already holds the language (a file with only the language is read as before) and the pictures keep their size. 4 tests of the file.

## [0.1.0] - Spindle warnings of the server and the head of the drill on screen

- **What the server tells the run screen:** a job on the server shows the excesses of the spindle that the server cut (`spindle_warnings` of its view, one short text for each: the tool, the value asked for and the limit) under the progress, and, when the machine has the node of a drill head, the turns of the spindle and its temperature, asked of the server every two seconds and let go if the machine has no node or the node does not answer. The line is named in all 37 languages. 2 tests.

## [0.0.9] - No console window on Windows, hot keys in 37 languages and the tools that are off sent to the server

- **No black window on Windows:** the program no longer opens a console; started from a terminal it attaches to it, so the help and the errors are printed there as before.

- **`voice:LANG:f|m` accepts the 36 languages with a folder of voices:** the list of languages with spoken notices grows from the first eight to every language of the interface that has a code (including `pt-br`), so a folder of voices with a language added is offered in the lists of sounds. 1 test.

- **Hot keys in the 29 languages read from files:** every label that has a highlighted letter in English now has one in each of them (`~X~` in `locales/*.tsv`), written by the new `tools/make_hotkeys.py`: the first letter of the word that no other control of the same screen uses, in the alphabet of the text (Latin, Cyrillic or Greek), keeping free the six keys the teach window keeps for its arrows and not repeating a Latin and a Cyrillic letter that look alike. `--check` fails when a file would change. A variant (Brazilian Portuguese, Canadian French) keeps the letters of its main language for the words it does not change.
- **Cyrillic and Greek letters can be typed:** `Lang::hot_key` reads a typed letter in either case, ignores the Greek accent, and takes a Latin key as the letter that sits there in the standard Russian, Ukrainian or Greek layout, so both keyboards reach the same control; the keys of the arrows of the teach window follow the same places. Bulgarian and Serbian need their own Cyrillic layout. The console, the window and the menu bar use the same rule.
- **Tests on 37 languages:** the hot letters of every screen (main, parameters of both programs, tools, panels, files, quit, interrupted job and teach window) are unique in all 37 languages, every text has no mark or one pair and has it when the English one has it, the teach buttons leave the arrow keys free, and a Russian and a Greek letter work when typed. Three letters of the routing window of the Spanish, Italian and French texts that clashed with another control were changed (`Án~g~ulo cuerda` is now `Á~n~gulo cuerda`).

- **The tools that are off go to the server too:** a job sent to the EH3D server (`connection = server`) carries `skip_tools` along with the holes the program chose, so the server leaves the same tools out and never asks the operator for them (`app::server_drill_request`). 1 test.

## [0.0.8] - 37 languages and tools that can be left out of a job

- **Room for 37 languages:** `i18n::Lang` lists the eight languages of the program and 29 more (Europe and America, with Brazilian Portuguese and Canadian French as languages of their own), and the words of the new ones are read from the files of `locales/` (`Text.Name` or `CText.Name`, one line per text), with English, or the main language of a variant, for what a file does not have; the list of languages of the program scrolls. The hot-key marks `~X~` are not used in the new languages.

- **Tools switched off:** `JobOptions::skip_tools` leaves the holes of the drills that are listed out of the job (`select_holes`), so a modern interface can drill only some of the tools. 1 test.

- **Two sounds for the visual check of the board:** `sound_check_ok` and `sound_check_bad` in the machine file, with the same settings as the other two (off, `default`, `tone:N`, a WAV file or `voice:LANG:f|m`) and two new cues in the library of sounds: a short rise for a check that is correct and three low falling notes for one that is not, the sixty sounds of the catalogue for each, and the recordings `check_ok.wav` and `check_bad.wav` of the voices (a voice without them plays the beep). The program of EH3D-BUNGARD-GUI uses them.

- **Which paths are the outside of a board:** `job::outer_paths` flags the closed paths whose box does not lie inside the box of another closed path, so the tabs of a panel go only on the outside of each board and not on the pockets, slots and tracks inside it.

## [0.0.7] - Spoken notices, the node of the drill head and a table that is not flat

- **Spoken notices:** the sound of the end of the job and of the tool request can be a voice (`sound_finish = voice:es:f`, language and female or male), found in the folder `voices` next to the program (or the one the variable `EH3D_VOICES` names); a voice that is not recorded plays the tone, and the program can list the voices that are there.
- **The node of the drill head in the machine file:** `head_node` (`off`, `direct` or `server`), `head_address`, `head_token` and `head_camera` say how EH3D-NODE-BUNGARD-AUX is reached; they are written only when the node is used, and the other lines of the file stay as they are.
- **A table that is not flat:** the options of a job can carry the height map of the table, and every hole is drilled to the same depth into the board wherever the table is high or low (`plan_drill_job_levelled`); without a map nothing changes.
## [0.0.6] - The connection drop-down, a blinking cursor, tabs for panels, jobs that go on and the machines of the fleet

- **A job can go on:** the options of a job tell how many of its first holes are already done, and the job leaves them out; the desktop window opens maximized.
- **Tabs for the outside of a panel:** a panel can carry tabs (how many on each side, how wide, spread evenly, near the ends or together in the middle) and the routing of its outside is cut into the pieces between them, so the boards stay joined to the panel until they are broken out.
- **The connection chosen in the Config window:** a drop-down with the five ways the job reaches the machine (the simulator, the serial port, a USB adapter, the EH3D node, the EH3D server) and what each needs (a port, an address and a token, a machine of the server); it is checked, applied with OK and written into the machine file without touching its other lines. The same for EH3D-ROUTEPRO.
- **A blinking cursor:** the cursor of a field being edited blinks. The same for EH3D-ROUTEPRO.
- **`--keys` takes `tab` and `backtab`:** the pictures of the windows that need them.
- **The order of the holes:** the classic screens tell, through `hole_order`, the holes of the job in the order the machine drills them, so a window that draws the board marks the right ones.
- **Several machines and stations at once:** with `connection = server`, `drillpro --machines` asks the server for the whole fleet in one request and lists every machine, grouped by station, with what each one is doing, its job and the jobs ready; `--machine ID` sends the jobs to that machine instead of the one in the machine file; the client reads the answer with `eh3d-fleet` (tested on a server that answers one request, and against the real server in EH3D-SERVER).
- **The buttons answer to the pointer:** the button under the pointer lights up, and while it is pressed it sinks (it loses its shadow, goes darker and moves its letters a little); `--point COLUMN,ROW[,down]` puts the pointer there for the pictures.
## [0.0.5] - The machine files from a shared crate, sounds for the end of the job and the tool change, more patterns in the file window and screenshots

- **The classic main screen names the program that runs:** the heading under the logo says which program it is (the routing program no longer says it is the drilling one).
- **Screenshots in the README:** three pictures of the classic screens (the main screen, the tool data and the parameters) in all the eight languages of the README.
- **More patterns in the file window:** an engine can add patterns after its own (the routing program adds the drawings of a board), which the arrow next to the file name lists with `*.ZIP` and `*.*`.
- **The files of the machine come from a shared crate:** the drill file, the tool table and the machine configuration are read and written by `eh3d-bungard-formats` of EH3D-COMMON (the same code that ROUTEPRO and the modern interface use); nothing changes for the operator.
- **Sounds when the job ends and when the machine asks for a tool:** `sound_finish` and `sound_tool_change` in the machine file are each off (the default), `default` (a tone the program makes, one for each cue) or the path of a WAV file of the operator's. The sound is played by the system (PowerShell, `afplay`, `paplay`/`aplay`/`play`) in a process of its own, so it never stops a job. It is explained in the machine file and in the guide of the configuration in the eight languages.

## [0.0.4] - Jobs in ZIP archives, an Offset window that moves the machine, file patterns and a simulation at the speed of the machine

- **The simulated job follows the clock of the machine:** the engine can be advanced by seconds of machine time (`tick_for`), so a move on the simulator takes as long as it would on the machine, with the feeds and the speeds of the tools, instead of running as fast as the computer can.

- **A lighter debug build:** the `dev` profile keeps the file and line of a panic (`debug = "line-tables-only"`) but not the full debug symbols, so the `target` folder of a test run is about a tenth of its size.
- **The Offset window moves the real machine:** with a real connection (RS-232, USB-RS232 or the node) the machine homes when the Offset Teach window opens, follows every move of the window (X, Y and Z, in steps of 1, 10, 100 or 1000 mil) and goes home again with the drivers off when the window closes; the window says when it is homing and shows a failure of the link. Through the EH3D server the window does not move a machine and says so. On the simulator it only follows the position on the screen, as before.
- **The arrow of the file name opens a list of patterns:** `*.NCD`, `*.ZIP` and `*.*` (`*.DTD`, `*.DCF` and `*.*` for the tool and configuration files); the list of files follows the pattern, and job archives are listed when the pattern asks for them.

- **Buttons that did nothing now work:** Start and Panelz. without a file say "Load a file first" in a window instead of staying silent; the Load button of the Tool Data and Parameter windows opens the Select File window for the tool files (`*.DTD`) or the configuration files (`*.DCF`) of the program and loads the one chosen, saying which; the arrow at the end of the name field of Select File gives the keys to the list of files.

- **Jobs packed in ZIP archives:** the Select File window lists the `.zip` files of a folder like folders, goes inside one with Enter (or by typing its name) and shows the drilling files in it; a file is taken out into a work folder and loaded as any other. `drillpro JOB.ZIP` loads the first drilling file of the archive. The archive code is the shared `eh3d-archive` crate of EH3D-COMMON, which never lists a name that could leave the work folder.

- **A metric header is read as metric:** the `METRIC` line of the header of a drill file begins with an M and was taken for a command, so the diameters of such a file were read as inches. Now it is read as it says.

- **The build, build-test and test scripts show a live panel:** a banner with the name and version, one line per step with its time, the number of tests that passed and a summary at the end, with the whole output kept in a log file. `test.sh` and `test.bat` run only the tests and never change the version; without `tools/pretty_run.py` the scripts behave as they always did.

## [0.0.3] - The Offset teach-in, the tool changer of the ATC models, examples and a 32-bit Windows build
- **A basic configuration and examples in every release, and Windows 32 bits:** the packages now carry the machine and tool files with every line explained in plain words, a guide to them in the eight languages, the example connection file and an `examples` folder of drill files from one hole to twenty thousand; all of it is generated by scripts in `tools/` and read back by a test. The release builds also include Windows 32 bits (not tried on a 32-bit Windows).
- **The operator's dialogs in the classic screens:** the job asks, as the original does, to confirm that the spindle may start (Attention!) and, for every tool, to put it in (Tool Change: the tool, the length of the run, the spindle, the Z speed and the stroke), with Ok and Abort on the keyboard (`Enter`, `Esc`, the letters) and the mouse. The simulation stops there too, so the whole flow can be seen without a machine. Before, a job on a real machine had no way to answer these dialogs from the classic screens (the menu-driven interface did) and would wait for ever.
- **The tool changer of the ATC models (basic):** when the configuration file has the "Tool change 1=Auto" line and the rack positions, DRILLPRO changes the tools by itself: for every tool the head goes to the place of the tool that is in the chuck (place 0, the test pin, at the start), lowers Z, opens the chuck with the auxiliary output, slides to the place of the next tool, closes the chuck and goes on to the first hole; the last tool goes back to its place. The Parameter window has the **AutoChg** box of those models (`U`, or a click). A job with more tools than places in the rack is refused with a message. The sequence follows a recording of the original on an ATC model, event by event; **it has not run on a real ATC machine**, and the test pin, the drill break detector and the tool-damage check are not done yet. The manual models are not affected: the job they get is the same as before.
- **Steps on a half step:** a hole that falls exactly half way between two steps now rounds to the even step, as the original does (it showed in the recording of the changer).
- **Vacuum cleaner on the auxiliary output (optional):** `vacuum = aux` in the machine file switches the auxiliary output (latch A bit 5) on with the spindle, at its speed, and off with it. The default, `vacuum = central`, writes exactly what the original software writes on the manual machine (which never touches that bit: a relay wired to the control unit follows its spindle bits).
- **The Offset button works:** it asks "Delete old offset?" (Yes starts at home, No at the offset in the form) and opens the Offset Teach window as the original has it. The head moves in steps of 1, 10, 100 or 1000 mil (0.001 inch) with `E`/`S`/`D`/`X` (Y+, X-, X+, Y-) or the arrow keys, `R`/`C` or `PageUp`/`PageDown` for Z, `1`-`4` for the step, and the mouse on every button. The position is shown in mm and Z as the depth left. **Ok** writes the position into the Offset fields of the main screen. **Teach** starts the Teach-In mode: positions are relative to the point where it was pressed, `+ Pos` records the head position, `- Pos` takes the last one back, `Mod` puts the last one where the head is, and Ok asks "Write Teach-In file?" and writes `TEACH.NCD` (a drill file this program reads). Screens checked against the original.
- **Esc during the job asks what next:** as the original does, `Esc` while drilling or routing opens INTERRUPTED / What next? with Cont. and Abort (keys `Enter`/`C` and `Esc`/`A`, or the mouse). The job waits, with the machine still, until the operator answers; Abort stops it and brings the form back. Before the first move (homing) `Esc` still stops at once.
- **The mouse wheel** scrolls the file list (window and console).
- **The percentage** of the job window counts the holes done, as the original does.
- **Moving through the folders of the computer:** the Select File dialog lists the files, then the folders, then `..\` last, as the original does; it works from the absolute folder (a folder written as `.` could not go up before), shows the drives as `[-C-]` entries on Windows, hides dotted files, ends a long name with `~`, and tells when a folder cannot be opened. A path written in the name field (`D:\jobs\*.NCD`, `..\other`, `C:\`) goes to its folder and takes the rest as the pattern or the file; the name field takes a path of any length. The mouse wheel scrolls the list.
- **The form drives the job:** the vectors `from` and `to` choose the holes (or paths) that are done, the clip leaves out the ones that end outside the working area (counted), and the Panelization dialog's Ok repeats the job over the copies, a tool at a time so that there is one tool change; the copies are `board - spacing` apart, as the original's count works out.
- **The job window shows the job:** the position, the tool, its stroke, the speeds, the count and the drilled depth follow the planned job (the values are the planned ones, not read from the machine).
- **Enter walks the form:** accepting a field goes on to the next one, as in the original.

## [0.0.1] - First version: file readers, job planning, text-mode interface and a simulated machine

- **Excellon reader:** `.NCD` drill files with or without the `M48` header, modal coordinates and imperial units of 1 mil, with the tool table (`.DTD`) and the machine configuration (`.DCF`).
- **Job planner:** orders the holes as in the file, X first, Y first or by shortest path, grouped by tool.
- **Interface:** an 80x25 text-mode screen with CGA colours, menus, a file dialog and a vector view of the holes, in eight languages (English, Spanish, Italian, German, French, Portuguese, Chinese, Japanese).
- **Protocol library (`eh3d-drillpro-protocol`):** byte transport (serial port or simulator), motion planning in millimetres with acceleration ramps, and a safety gate that refuses motion until it is armed with verified settings.
- **Simulator:** the whole job runs to the end without hardware.
- **Real machine:** a machine file (`machine.cfg`, shared by DRILLPRO and ROUTEPRO) chooses the simulator, the computer's serial port, a USB serial adapter or the EH3D-NODE-BUNGARD; every tuning value lives in it. `Esc` stops a drilling job and switches the drivers off, and a red banner says the machine is real.
- **Reference run:** Z, X and Y to their limit switches with the control unit's "all home" line read once the last search has gone out (reading it in the middle of the stream made the Y motor lose steps on the CH340), a short unstick move when parked, a Z search that covers the whole travel (`z_search_steps`) and a smooth calibration jump. Tried on a Bungard CCD MTC; the CCD/2 MTC is driven the same way and has not been tried. Spindle and vacuum outputs have not been tried; the two ATC models are not covered.
- **Spindle of the node:** `spindle = node` in the machine file makes the job ask the EH3D-NODE-BUNGARD for the spindle (a variable-frequency drive on the node's own outputs, any speed up to the node's maximum) instead of writing the control unit's spindle bits; the spindle is stopped on any stop. The node link also reads the machine's lamps and can ask the node to drop the rest of a search as soon as an axis is home.
- **Server connection:** `connection = server` sends the drilling job to the EH3D-SERVER, which plans it with the constants of the machine, runs it through the machine's node and tells the program how it goes; the program shows the progress, answers the dialogs and can stop the job, and closing it does not stop the job.
- **Steady motion:** moves go out as one continuous stream paced by the adapter's UART, Z moves byte by byte.
- **Documentation:** protocol notes, the connection guide with the CH340 findings, and a machine file example with every value.
- 123 tests, `cargo clippy -D warnings` and `cargo fmt --check` in CI on Linux and Windows, and a repository check of the manifest, the versions, the changelog and the eight README files.
- **Ready-made packages for Windows, Linux and macOS:** the `Release binaries` workflow builds the program with its window for Windows (zip), Linux (tar.gz; X11 and Wayland) and macOS (Apple silicon and Intel, tar.gz), each package with its SHA-256, and the release carries them.
